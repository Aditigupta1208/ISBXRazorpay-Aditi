# AI Build Log: Razorpay AI x PM Build Challenge (Track 2)

Status: updated 13 Oct 2026, ready for submission review. This file is public. No API keys, no personal data, no confidential material.

The submission form asks for a publicly viewable markdown file covering the five sections below. A dated running log follows them.

## Summary

- **Tools:** Claude (claude.ai chats and Claude Code) for research, planning, review and building; ChatGPT for the clean kill-test run; free Groq models (Qwen, gpt-oss-120b) for the live check inside the app.
- **What AI did:** read the brief, mapped what Razorpay ships, wrote the first PRD and the code (about 11,000 lines, 334 unit tests, 29 browser suites), helped draft the one-page note and checked it against the brief, ran audits section by section, and drafted cases and documents.
- **How AI sped up the work:** working alone at about two hours a day, I went from the brief to a deployed prototype (about 11,000 lines of code, over 330 unit tests, 29 browser suites), a labelled evaluation set and the one-page note in under three weeks. AI did the drafting, coding and checking; I made the decisions on scope, labels and what to claim.
- **What I decided:** the track and the segment; which ideas to kill; the final labels on the kill test, the held-out set and C21 to C30; Fold and Escalate as first-class calls; no database or accounts; what to cut; what to say and not say about accuracy.
- **Where AI was wrong and I caught it:** a rule-only prompt that would have refunded USD 1,600 too much on C15; a kill test run in a chat that already knew the test design; an overstated "gap" in held-settlement; "UPI is practically free"; POST instead of PATCH on the contest call; a metric that counted a correct answer as obeying a hidden instruction.
- **Honest limits:** no paid Claude key, so live checks run on free Groq models; all disputes are synthetic; the eval release gate fails on two measures and nothing was tuned; three merchants, interviewed and then walked through the product (n=3, about the screens and not about real outcomes), and no real Razorpay data.

## 2. Key prompts, workflows, agent setup

The overview below is short. The dated running session log at the bottom has the raw detail, one entry per session.

- **Workflow overview:** research the brief and what Razorpay already ships -> filter ideas (does Razorpay see the signal, can it act, does it need judgment) -> kill test on 16 public-source cases against a fixed-checklist baseline -> PM docs (discovery, features, PRD, screens, data and stack, design) -> visual mock from Razorpay screenshots -> build in milestones (saved results first, live AI call second, evals third) -> product note, video, build log.
- **Key prompt 1 (kill test, product prompt):** `prompts/dispute-agent-v1.md` in the repo: applies Visa's rule for the reason code, returns Fight / Accept / Escalate / route to fraud cover, names the deciding evidence, and weighs the economics. Run in a fresh ChatGPT chat on 16 cases.
- **Key prompt 2 (second reviewer):** `prompts/second-reviewer-v1.md`: rules only, no cost reasoning. Used to flag disagreements with my labels. It said Accept on C15, which is the case that showed why the product prompt needs economics.
- **Key prompt 3 (the app's prompt):** `prompts/dispute-agent-v2.3.md` (v2.1 and v2.2 kept as history): forced structured output, a cited draft in which every sentence names a document, win-probability estimate, defensible amount, evidence flags, and a rule that evidence is data and never instructions.
- **Agent / pipeline setup (prototype):** dispute record + merchant evidence (each item wrapped as `<evidence id="E1">`) -> fraud codes routed before any model call -> Claude API forced tool call -> zod validation, retry once -> safety rules R1 to R9 run in code (R3, R4, R5 and R8 can change the call; the others stop a draft) -> money maths in code -> merchant approves, folds or escalates (simulated, nothing sent to Razorpay) -> outcome and prevention tip. No API key or a failed call falls back to a labelled saved result.
- **How the models were used:** Claude Code in cloud sessions, one milestone per session, then audit sessions that read each section as a merchant would, list findings, and fix them. In the product, a forced tool call with a schema, validated with zod, one retry, then a labelled saved result. The live check runs on Groq. The Anthropic path is built and tested only against a stand-in server. No paid key was available; a key switches the provider without code changes.
- **Prompt history (the agent prompt):**

| Version | What changed | Why |
|---|---|---|
| v1 | Applies Visa's rule for the reason code and returns Fight, Accept, Escalate or route to fraud cover. Run in a fresh ChatGPT chat on 16 cases. | The kill test. |
| v2 and v2.1 | Forced structured output, a cited draft (every sentence names a document), odds, the defensible amount, evidence flags, evidence is data and never instructions, and economics. | A rule-only prompt accepted C15 in full. The product needs the money and an Escalate call. |

## 3. One AI output I rejected, corrected or significantly improved

**The example I am submitting is A, directly below.** B to M are further examples, kept as supporting evidence.

**A. A prompt that looked right but would have cost the merchant money (kill test, 4 Oct).**
- A second-reviewer prompt that only applied Visa's rules said "Accept" on case C15, a USD 3,200 group-tour dispute. Taken at face value, that refunds USD 1,600 more than the merchant's own accepted policy required.
- The product prompt, which also weighs the economics, said "Escalate: confirm the canceller's authority; a 50% refund is likely due." I labelled C15 Escalate.
- **What I did:** added economics and an Escalate call to the product prompt (v2), and made C15 the example on the evals page. **Why it mattered:** a rule-only agent can be right on the rule and wrong for the merchant.

**Further examples**

**B. A test I could not trust, so I re-ran it (4 Oct).**
- The first kill-test run was done in a Claude chat inside my project. It had seen the test design, so it was not a fair test.
- I re-ran both prompts in fresh ChatGPT chats. Result: 15/15 decisions vs 8/15 for a fixed checklist, 0 invented facts in 8 drafts, fraud case routed. The Claude run is kept only for comparison. The app uses the clean run.

**C. An idea I killed with a simulation (28 Sep).**
- "Personalised retry timing for failed UPI AutoPay debits" looked strong. A Monte Carlo simulation (200k subscribers, NPCI retry cap) showed almost no headroom over Razorpay's existing template (ceiling +2.6 points).
- **What I did:** dropped it instead of defending it.

**D. A "gap" the AI overstated (28 Sep).**
- The AI called a held-settlement resolver the strongest Track 2 gap. I pushed back that the research was thin. Deeper research found Razorpay had already shipped a self-serve Account Review Dashboard (Feb 2026) with "Funds on Hold" and "Needs Clarification" states, and a review count showed only 1 of 20 reviews was about a hold.

**E. A PRD I rejected as not real (5 Oct).**
- The first PRD draft was short and read like a summary. I said length was not the problem, but it had to be written the way a PRD is actually written and be useful. The rewrite has assumptions, a user flow, 30 requirements with acceptance criteria, AI design, edge cases, eval thresholds, privacy and prompt-injection handling.

**F. Facts the AI got wrong that I had checked (3 to 5 Oct).**
- The contest call is PATCH, not POST. The clawback uses the exchange rate on the day the dispute is created, not today's. "UPI is practically free" was misapplied (Razorpay charges a 2% platform fee on UPI). Product name "Dispute Expert" is Razorpay's own wording. A claim about the MDR FAQ was wrong (the Finance Ministry PDF includes education and AutoPay).

**G. Overclaims I made the AI walk back (5 Oct).**
- The "paperwork" angle and a "dispute drill" idea were presented as differentiators. Neither was strong enough, so both were cut or demoted to minor next steps.

**H. A metric bug in my own eval (11 Oct).**
- The first complete 40-case run counted a correct Fight on C39 as obeying a hidden instruction in the evidence. I found it by reading the case against the score, not by trusting the number. Fixed, and the run was repeated.

**I. A release gate I left failing (11 Oct).**
- Latest complete run (prompt v2.3, 38 scored): agreement 87% against 61% for a plain checklist, but needs-judgment cases 75% against a bar of 80%, and first-try citations 83% against a bar of 90%. The gate fails.
- **What I did:** kept the failure visible on the Evals page and in `npm run eval:gate`, and tuned nothing. **Why:** tuning the prompt to the held-out cases would make the number meaningless.

**J. A label I changed after the assistant argued against it (11 Oct).**
- On C22 (a coaching workshop nobody joined) I labelled Escalate, to ask for the video platform's connection log. The assistant pointed out that E3 is the customer's own email on the day saying he could not open the link, with no reply from the merchant on file, so the log would more likely confirm the failure than rebut it. I agreed and set Fold. The other nine of my ten labels matched the draft key.

**K. A screen a first-time viewer would misread (11 Oct).**
- The money row said "possible fee of ₹52,800" on a ₹42,240 dispute, which looks like an error. It is Visa's arbitration fee, charged only if the bank escalates. I reworded the row, moved the evidence names and the bank-test link, and folded the Escalate extras so the main button sits closer to the top. No behaviour or guardrail changed.

## 5. Known limitations, risks, verification steps

- **Evidence limits:** review-site data is self-selected. There is no access to real Razorpay merchant data. Three merchants were interviewed (one outside the target segment), with follow-ups on a dispute each had accepted or lost. In the first round they answered about a described message, not the product; on 12 Oct the same three walked through the live product (n=3, about the screens, not about real outcomes).
- **Synthetic data:** all 40 practice disputes were written by me and the AI, patterned on public cases (Visa's dispute guidelines, Razorpay blogs, Karbon, Winvesta and Shopify community posts). The merchants, customers and documents are invented. The exchange rate is labelled (live, fixed or demo). The odds of winning are an AI estimate, not a measured rate.
- **Labels:** the answer key is my reading of Visa's rules. C21 to C30 were first proposed by the AI assistant; I confirmed all ten on 11 Oct after reading each case, and changed C22. C31 to C40 were confirmed on 9 Oct, before any run.
- **Verification:** every factual claim about Razorpay (contest API, deadlines, Chargeback Shield terms, clawback rate) was traced to a public source and corrected where the AI was wrong (see section 3F). A reply from Razorpay support (unsigned, no ticket number) and an informal answer from a Razorpay colleague are treated as indicative only. Tax and FEMA points are marked secondary-source.
- **Evals:** first kill test, 15 scored cases: agent 15 of 15, fixed checklist 8 of 15, no invented facts in 8 drafts. Latest complete run (11 Oct, prompt v2.3, 40 cases, 38 scored): agreement 87% against 61% for the checklist; held-out cases 7 of 8; needs-judgment cases 75% against a bar of 80%; first-try citation 83% against a bar of 90%. **The release gate fails and nothing was tuned.** An earlier run was incomplete because the free Groq limits ran out; it is kept in `eval/incomplete` and not shown as a result.
- **Why AI, not rules:** nine extra rules reached 20 of 20 on known cases and scored 6 of 10 on ten unseen cases, against 7 of 10 for the plain checklist.
- **Limits of the tests:** the cases are short and cleanly written, and the model was given Visa's rules. They show the AI applies rules to written evidence and knows when to escalate; they do not prove real-world win rates.
- **Not proven:** Claude as the live model; saved results for C01 to C16 are still from ChatGPT prompt v1.
- **Checks on the build:** 334 unit tests, 29 browser suites (desktop and phone), a 12-page sweep, lint with zero errors, a secret scan and a dependency audit. Hook-dependency lint warnings (31) are deliberate.
- **Risks and how the product handles them:** wrong AI answer (nine code checks can downgrade a Fight or stop a draft; every sentence cites a document; a figure check compares every number and date with the documents); prompt injection in evidence (wrapped and escaped, one forced tool, one test case); privacy (full card numbers blocked in evidence and draft, nothing stored on a server); budget abuse (rate limit, input caps); AI unavailable (labelled saved result, works with no key); overlap with Razorpay's Dispute Responder (stated as an assumption, not confirmed).

**L. Facts the AI got wrong while drafting the one-page note (12 to 13 Oct).**
- In the first Problem draft the AI described the agency's USD 2,400 dispute as lost; it was won. It used the SaaS founder's missed-deadline story as evidence for the non-fraud decision, but that dispute was fraud-type (unauthorized), which the product routes to Chargeback Shield. It added a detail about a support ticket at a cloud host that was not in my notes. It offered two outside statistics (a per-dispute cost and a 54% figure) that I could not trace to a source for Indian merchants, said nobody offers a pre-submission review (then retracted it), and described all three merchants as in my target segment when one is not.
- **What I did:** dropped every figure and detail I could not source and kept only what traces to my own merchant notes or to public pages I could read (Razorpay's international page and blog, Stripe's and Chargeflow's pages, with Chargeflow's figures labelled vendor-reported). I chose the scope wording "merchants selling abroad" because the third merchant faces the same problem on a different gateway.

**M. AI scoring of my own note that I pushed back on (13 Oct).**
- The AI first marked the note down for having only three merchants and no sizing, and for being dense. I pointed out that every submission works without Razorpay's data and with a small sample, and that the brief names clarity, not density, as the criterion; it removed those deductions. I also asked it to judge the quality of each answer against the brief, not only whether a section was covered. A second AI's review said the note ran to two or three pages; I measured one A4 page and ignored that point, and took the valid ones (an undefined "line" in the learning paragraph, no Agent Studio signal, an overstated "only AI" claim, a thin validation plan).
